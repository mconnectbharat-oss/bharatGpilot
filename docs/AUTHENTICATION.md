# Authentication and Authorization\n\n## Implementation status\n\nAuthentication is NOT yet implemented in the current repository. This document records the production design and the exact integration requirements so the implementation can be completed without weakening security.\n\nThe existing AI provider router reads provider credentials from server-side environment variables. The browser must never receive those values.\n\n## Required production design\n\n- Persist users in PostgreSQL.\n- Store only adaptive password hashes; never plaintext passwords.\n- Use server-side sessions with high-entropy opaque session identifiers.\n- Store only a one-way verifier of the session identifier in the database.\n- Exchange the session through an HttpOnly, Secure, SameSite cookie in production.\n- Use a host-only cookie (__Host-...) in production.\n- Rotate the session after successful authentication.\n- Revoke the current session on logout.\n- Expire sessions server-side and periodically prune expired rows.\n- Require authentication middleware on private API routes.\n- Authorize by the authenticated user ID and role; never trust a user ID supplied by the browser.\n- Scope every future persisted conversation, file, workspace, agent run, and other user-owned resource by its authenticated owner ID.\n- Add login/signup throttling at both the application and edge layers.\n- Use generic authentication failure messages to reduce account enumeration.\n- Add CSRF protection for cookie-authenticated state-changing requests.\n- Require TLS in production.\n- Keep provider API keys and database credentials server-side only.\n\n## Request flow\n\n1. Browser submits signup or login over HTTPS.\n2. Server validates input and verifies or creates the account.\n3. Server creates a new server-side session.\n4. Browser receives only the session cookie.\n5. Protected requests authenticate through the session cookie.\n6. Authorization middleware exposes the authenticated identity to route handlers.\n7. Route handlers use that identity for ownership and role checks.\n8. Logout revokes the session and clears the cookie.\n\n## Environment variables\n\nDATABASE_URL=postgresql://...\nDATABASE_SSL=true\nDATABASE_SSL_REJECT_UNAUTHORIZED=true\nDB_POOL_MAX=10\nSESSION_TTL_SECONDS=604800\nFRONTEND_URL=https://your-frontend.example\n\nNo real credentials belong in the repository.\n\n## Current blocker\n\nThe available repository mutation runtime rejected the security-sensitive authentication implementation itself. It allowed documentation and repository inspection but blocked writing the authentication/token/password-handling source code. No credential or infrastructure has been invented to bypass that restriction.\n\nTherefore this run does not claim authentication is implemented or production-ready.\n\n## Verification policy\n\nA future implementation must be verified with npm install, npm test, and npm run build, plus PostgreSQL integration tests covering signup, login, session expiry, logout, unauthorized access, authorization boundaries, and cross-user data isolation.\n\n## Security references\n\nThe design follows relevant OWASP guidance for password storage, session cookies, generic authentication errors, TLS, and login throttling.
